## 02 / 需求、场景与应用价值

### 目标用户与任务

目标用户是需要阅读英文机器学习论文、追踪研究方向并整理写作材料的学生。核心任务不是得到一段流畅回答，而是得到可以回到原文核查、继续整理和复用的研究材料。

| 真实任务 | 原有摩擦 | 知研中的闭环 |
| --- | --- | --- |
| 核对训练配置 | 聊天结论与PDF位置脱节 | 选文献→检索→回答→引用→原文坐标 |
| 管理不同版本 | 改名文件和版本修订难区分 | 哈希查重→内容比较→版本提示→用户保留 |
| 跨语言阅读 | 阅读、翻译与引用分散 | 原版面与段落对照→缓存译文→引用跳转 |
| 整理研究产出 | 草稿与图片失去来源 | 引用随草稿保存→编辑→图表/代码导出 |

### 验收型需求

回答必须携带可打开的出处；生成失败不能显示假结果；重复文件不能悄悄产生重复记录；长文档可以按页读取；中断翻译可利用已完成缓存继续。这些需求都可通过界面或自动化检查观察。

范围依据：用户要求从零开发、双赛共用、无付费API、先本地运行。没有用户访谈样本或效率提升百分比，本文不虚构这些数据。


## 03 / 意图控制与上下文管理

### 实际用户输入与角色分工

真实指令包括“从零开始。两个都做，全部由你来完成”“都没有，先做本地可运行版”，以及“补齐所有需要的内容”。参赛者给出目标与资源约束；AI助手自主拆分任务、生成代码和执行修复。下述策略是实际工作流的整理，不伪称每一步都是参赛者追加的Prompt。

| 上下文层 | 约束内容 | 对实现的影响 |
| --- | --- | --- |
| 产品意图 | 科研助手；两个赛道共用实现 | 统一来源模型，分别制作过程与技术材料 |
| 资源条件 | 没有API和服务器，先本地可运行 | Ollama、本地模型、SQLite、回退检索 |
| 接口契约 | 文献ID、块ID、页码、bbox及来源编号 | 阅读、问答、翻译、写作共享定位方式 |
| 修复上下文 | 保留失败输入、实际输出及相关源码 | 缩小修改范围，以原失败样例复测 |
| 验收上下文 | 自动化、真实模型、浏览器分别记录 | 区分控制流通过与生成内容质量 |

### 防止上下文漂移

检索证据与用户任务分开传入模型；资料中的命令不作为操作指令。原论文参考编号与系统证据编号明确分离。跨篇比较按论文轮转选取正文，避免上下文被单篇占据。

原始记录：artifacts/process-evidence/public-dialogue.md；implementation-calls.jsonl。系统指令和内部推理不作为公开过程材料。


## 04 / 架构约束与数据契约

React工作台 → FastAPI接口 → 解析 / 检索 / 任务 → SQLite + PDF → Ollama模型

界面负责交互与状态呈现，服务端负责文献、任务、模型和导出。解析层首先生成来源锚点，后续模块依赖统一契约，避免每个页面重复构建一份无法对齐的数据。

| 对象 | 关键字段 | 设计作用 |
| --- | --- | --- |
| 文献 | id、sha256、版本、状态 | 文件身份、重复检查、可恢复处理 |
| 内容块 | doc_id、page、bbox、ordinal、text | 页内定位、阅读顺序、证据共享 |
| 译文 / 公式 | chunk_id、text或latex、model | 绑定来源块；保存模型与校对状态 |
| 回答 / 草稿 | text、sources、trace | 内容、出处、执行过程分离 |
| 追踪主题 | next_run、last_run、error | 进程重启后检查到期任务 |

### 架构约束如何落实

模型提出的工具名称和参数由服务端复核，不执行任意生成程序；同进程模型调用串行；PDF页面按需渲染；生成结果与检索原文分别标识。前端对公式和图表按需加载，降低首屏资源负担。

代码：app/db.py、main.py、parser.py、research.py、llm.py；界面：src/main.jsx、research-tools.jsx。


## 05 / 核心迭代链一：可信问答

### 目标 → 失败 → 修复 → 复测

目标是让中文问题能查询英文论文细节，并能返回原文。初期模型混用了论文参考编号与检索证据编号；推理模型也出现预算耗尽、没有最终正文的情况。跨篇比较还曾把问题对象换成证据中的第三种模型。

| 修复环节 | 实际策略 | 可观察结果 |
| --- | --- | --- |
| 引用编号 | 送入模型前区分两套编号，拒绝越界输出 | 不合格回答不作为可信结果展示 |
| 最终正文 | 分离thinking与content；检查长度截断 | 保存错误状态，允许重试或查看原文 |
| 跨篇证据 | 每篇正文候选分组轮转，限制总量 | Transformer与BERT均进入上下文 |
| 数值适用范围 | 逐项提取数值、单位、对象，复核共同条件 | 修复将“所有模型”误判为证据不足 |

### 真实验证与限度

最终录制回答得到：base和big均使用8块P100，分别训练12小时和3.5天。跨篇回答覆盖Transformer的注意力结构与BERT的双向编码器承袭关系。引用校验只检查编号有效性，仍需人工核对论断是否被证据支持。

实施链：01-来源与模型校验.json。修复：f752189、025f086。证据：overcautious-answer-failure.json、final-agent-answer.json、multi-paper-balanced-validation.json。


## 06 / 核心迭代链二：公式转写

用户要求补齐功能后，AI将“保留原文公式候选”扩展为“原图转LaTeX、渲染、编辑和保存”。第一次真实识别漏掉了Attention公式末尾的V：PDF将分子、分母、末尾因子拆成独立文字块，单块裁剪不完整。

截图证据：artifacts/screenshots/formula-final.png

### 修复决策

不靠在结果后硬补字符，而是在裁剪阶段合并同一垂直公式带内的相邻短块，再放大原图交给视觉模型。修复后转写保留softmax表达式、分母根号和末尾V；前端通过KaTeX呈现，用户能对照原始PDF修改。

实施链：02-公式转写与裁剪修复.json。代码：app/formulas.py。失败及复测：formula-first-crop-failure.json、formula-live-validation.json；一次修复后调用7.94秒。该样例不代表所有公式零错误。


## 07 / 核心迭代链三：追踪与绘图

### 把页面功能补成可持续流程

针对“补齐所有需要的内容”的要求，发现模块增加持久化主题、周期刷新与未读结果；写作模块增加可编辑草稿、结构图预览和五类图表。核心约束是结果来自真实接口与上传数据，不能用演示假数据伪装功能成功。

| 问题 / 验收点 | 实现 | 实际验证 |
| --- | --- | --- |
| 关闭浏览器后仍需追踪 | 后台线程每30秒检查到期主题 | 真实主题保存12条arXiv结果 |
| 重复抓取与网络失败 | 唯一键去重，失败15分钟后重试 | 重复、暂停与错误状态测试 |

## 09 / 工程质量与失败恢复

| 风险 | 产品与工程处理 | 检查方式 |
| --- | --- | --- |
| 解析途中退出 | 记录中断状态，允许重新解析 | 文献状态与页面读取 |
| 翻译取消竞态 | 仅领取queued任务，保留已完成缓存 | 取消不重启；续传不重复生成 |
| 模型不可用 | 显示调用失败，保留原文检索 | 不以固定答案冒充生成结果 |
| 生成引用越界 | 阻断不合格输出 | 有效/无效引用两类测试 |
| 公开样例被破坏 | 独立评审库、口令、限制库内文件变更 | 未登录401；受保护操作403 |
| 资源冲突 | 单进程模型锁、分块索引、按页渲染 | 长书末页可读取 |

### 对黑盒的控制范围

白名单与输出检查控制执行边界，来源锚点支持人工复核。当前是有界工具规划，不是无限循环自主Agent；图谱只覆盖已解析匹配的本地引用。明确这些范围，才能把可用性问题定位到具体层次。

## 13 / 方法贡献与应用扩展

### 贡献一：来源契约贯穿全流程

来源块不仅用于检索，还用于阅读定位、公式校对、翻译缓存和写作出处。统一契约使AI生成的新模块能复用同一证据，减少跨模块对应关系的维护成本。

### 贡献二：把失败样例变成开发约束

编号混用推动证据边界约束；公式缺因子推动裁剪上下文补全；多文比较偏题推动证据均衡。三条链体现从实际错误到可检查修复的过程，而非仅展示成功界面。

### 贡献三：在个人电脑上形成可操作闭环

本地模型与SQLite降低对云账户的依赖，结合公开论文发现、周期追踪与可复现图表，形成面向学生科研阅读的应用组合。此处创新是工程组织与交互集成，不主张发明BM25、PageRank或新基础模型。

### 下一步

优先扩大版式与公式测试、加强结论和证据之间的逻辑核验，再评估更长上下文和稳定部署。迭代仍以真实用例和可复查指标为依据。
